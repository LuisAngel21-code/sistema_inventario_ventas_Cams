6.1. Estrategia y plan de pruebas

El aseguramiento de la calidad del sistema Tienda Cams se organizo como una actividad continua dentro del desarrollo agil. Desde el primer sprint se definio que cada historia de usuario debia cerrarse con evidencia verificable, de modo que las pruebas no fueran un paso final sino parte del trabajo diario del equipo. Por esa razón, cada criterio de aceptación se convirtio en un caso de prueba con identificador propio y quedo conectado con al menos una prueba automatizada.

La estrategia sigue la forma de una piramide. En la base están las pruebas unitarias, que verifican la lógica de los modelos sin depender de la interfaz. En el siguiente nivel están las pruebas de integración, que recorren las rutas, los controladores y la base de datos. Sobre ellas se ubican las pruebas de aceptación escritas en lenguaje natural con Behat, que reproducen los criterios acordados con el cliente. En la cima están las pruebas de extremo a extremo con Selenium, que abren un navegador real y recorren el sistema como lo haria un usuario.

6.1.2. Entornos y datos de prueba

Las pruebas se ejecutan en un entorno local sobre Windows, con PHP 8.3, Laravel 12, SQL Server 2022 Developer y Google Chrome. Para evitar que las pruebas de integración ensucien la información real se creo una base de datos independiente llamada tienda_cams_test, que se reconstruye desde el script principal del proyecto. Las pruebas de integración usan transacciones con retroceso automático, por lo que cada prueba deja la base tal como la encontro.

Las pruebas de aceptación y las de navegador trabajan sobre la base tienda_cams y crean sus propios registros con prefijos reconocibles, como BDD o SEL. Los usuarios de prueba son admin@cams.com, jefe@cams.com, almacen@cams.com y tienda@cams.com, todos con la contraseña cams2026 y con el mismo secreto TOTP de demostracion, lo que permite automatizar el segundo factor sin depender de un telefono.

Datos de prueba principales: sucursal Sucursal Behat, producto Cama Behat con stock por sucursal, código OTP calculado con el secreto JBSWY3DPEHPK3PXP y ventas de dos unidades para verificar el descuento de stock.

6.3.3. Detalle de los resultados

Las pruebas unitarias cubrieron el calculo de subtotales, el incremento y descuento de stock, la validación de códigos OTP, la vigencia de los tokens de recuperación y las comprobaciones de rol. Las pruebas de integración recorrieron las rutas de login, código, recuperación, sucursales, productos, stock, inventario, movimientos, ingresos, ventas e historial, verificando tanto los casos exitosos como los rechazos por datos inválidos.

Los escenarios de Behat se redactaron con las palabras del cliente y se ejecutaron contra la base real, lo que permitio comprobar el comportamiento de punta a punta sin depender de la interfaz. Finalmente, Selenium inicio sesión con los usuarios reales, resolvio el código de seis digitos con la libreria de autenticación y verifico los textos de confirmacion en cada pantalla.

Durante la ejecución se presentaron dos situaciones que quedaron documentadas. La primera fue un defecto funcional en el mensaje de stock insuficiente, corregido y registrado como DEF-01. La segunda fue una caida momentanea del servicio de base de datos por acumulacion de conexiones, que se resolvio esperando la recuperación del servicio y repitiendo la corrida; no afecto el resultado final.

CampoDetalle
IdentificadorDEF-01
Caso relacionadoTC-29 - Rechazar una venta que supera el stock
Severidad / prioridadAlta / Alta
DescripciónAl registrar una venta con cantidad mayor al stock, el sistema cortaba la operación con una excepción HTTP 422 y mostraba la página de error de Laravel, en lugar de volver al formulario con un mensaje comprensible.
Pasos para reproducir1. Abrir /ventas/nueva.
2. Elegir un producto sin stock.
3. Ingresar 999 unidades.
4. Registrar la venta.
Resultado esperadoVolver al formulario mostrando el mensaje Stock insuficiente para el producto indicado.

CausaEl controlador usaba abort(422) dentro de la transaccion en lugar de una excepción de validación.
CorrecciónSe reemplazo por ValidationException::withMessages, que revierte la transaccion y redirige al formulario con el error.

6.4.3. Lecciones aprendidas

La ejecución de las pruebas permitio detectar dos problemas que no se habian visto durante el desarrollo manual. El primero era de experiencia de usuario y afectaba directamente un criterio de aceptación. El segundo era de instalación y habria impedido que otra persona levantara el proyecto. Ambos se corrigieron antes de la entrega, lo que confirma el valor de automatizar las pruebas y de ejecutarlas sobre una base limpia.
